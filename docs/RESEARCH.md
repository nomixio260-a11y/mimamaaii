# 研究ノート: 超小型 AI に使える技術のサーベイと実験結果

制約: 標準ライブラリのみ、数百 MB 以下のメモリ、CPU 1 コア、学習はオンライン (逐次) で止まらない。
この制約の中で「賢さ」を上げるために、関連分野の技術を調べ、何を採用し何を見送ったかを記録する。
実験は `tools/experiment.py` と `tools/bench.py` で再現できる。

## 1. 言語モデル

| 技術 | 要点 | 判断 |
|---|---|---|
| 補間付き絶対ディスカウント + Kneser-Ney 継続カウント | 低次への後退を「その語が何種類の文脈に続くか」で重み付け。実装コストが低く、n-gram では今も標準 | **採用** (`lm.py`) |
| 整数パックした文脈キー | 文脈タプルを 1 個の整数にし、後続が 1 種類の文脈は辞書を作らない | **採用**。同一データで実メモリ 26.4MB → 8.8MB |
| Count-Min Sketch による乱択 LM (Talbot & Osborne 2007) | 高次 n-gram のカウントを固定メモリのスケッチに入れる | **不採用 (負の結果)**。実験 [2] で、衝突により確率が正規化されず「見かけの ppl」が下がる。Bloom フィルタで存在確認を先に行う原論文の構成でないと成立しない |
| 接尾辞配列 (Infini-gram, Liu et al. 2024) | コーパス全体の接尾辞配列で任意長の n-gram を二分探索で数える | **採用** (`suffix.py`)。実験 [3]: 5 万トークンで構築 0.04 秒、45 bytes/token、16 万クエリ/秒。生成時に「最長一致 (2〜12 トークン) の続きの分布」を一致長に応じた重みで n-gram と補間する。自己評価 (ppl) には使わず生成専用 |
| 会話キャッシュ LM (Kuhn & De Mori 1990) | 直近数百トークンの減衰付き unigram/bigram を静的 LM と補間 | **採用** (`lm.CacheLM`)。会話の流れに沿った語を生成しやすくなる |
| Self-consistency / best-of-n | 候補を複数生成し、LM 平均対数確率 + 知識の語との重なり + 質問の句との重なり − 繰り返し で選ぶ | **採用** (4 本)。1 回の生成が 3〜5ms なので許容 |
| 純 Python の小型ニューラル LM (対数双線形 bigram + 負例サンプリング) | 埋め込み 32 次元、完全 softmax で評価 | **不採用 (負の結果)**。実験 [4]: 4 万ペア × 2 epoch で 15 秒 (5,300 token/s、n-gram の約 1/30)、ppl 121 vs KN-bigram 37。データも計算も足りない |
| numpy だけで書いた Transformer LM (`neural.py`) | 第 1 版: LayerNorm + 学習位置埋め込み + ReLU MLP (GELU は tanh と x³ で学習時間の 6 割を占めたので置換)。約 10,000 token/s、5 万トークンで ppl 996 → 75 | 第 2 版に置換 |
| LLaMA 系構成 (RMSNorm・RoPE・SwiGLU・重み共有) + サブワード語彙 + 系列パッキング + KV キャッシュ + top-p/繰り返しペナルティ + コサイン LR | 現代の小型 LLM の標準構成を手書き逆伝播で。勾配検査 (相対誤差 10⁻⁷)、KV キャッシュと全系列順伝播の一致 (10⁻⁸) | **採用 (任意依存、応答の主経路)**。base 2.9M params、3,500 token/s (共有 CPU)。77k トークン + 合成 QA で 6 分: 損失 0.99、取り置き ppl 7.3。RAG 形式で定義質問に正しい文を生成できる段階。汎化には桁違いのデータが要る |
| 記号処理系からの蒸留 (合成 QA) | 事実ストアの三つ組からテンプレートで質問を作り、答え (整形文) と文脈 (元の文) を学習例にする。知識グラフ → 言語モデルの蒸留 | **採用**。少データでも「Xとは？」に正しい定義を生成できるようになる主因 |
| 生成の受け入れ検査 | 接地率 (文脈/質問との句の重なり)、モデルの平均対数尤度、文末、崩れパターンで生成文を検査し、落ちたら検索応答に戻す | **採用**。小さなモデルの作り話を利用者に見せないための安全弁 |
| データ並列 (同期 SGD、共有メモリ) | numpy の要素演算は 1 スレッドなので、BLAS の多スレッド (1.4 倍) より fork したプロセスで別バッチの勾配を計算する方が効く。パラメータは共有メモリ、勾配もワーカーごとの共有メモリ、通信は損失値だけ | **採用**。4 コアで 3,474 → 8,979 token/s (2.6 倍)。実効バッチが workers 倍になるので学習率はプリセットごとに調整 |
| SiLU の再利用・AdamW のインプレース化・候補の一括生成 | 順伝播で計算した sigmoid を逆伝播で再利用 (exp 3 回節約)、AdamW の一時配列を 1 つに、n 本の候補を 1 回の順伝播で進める | **採用**。学習 +10%、生成 2 倍 |
| RAG の抽出練習 (copy examples) | 知識文をキーワード付きの文脈に入れ「その文を答える」例を作る。文脈を使う (コピーする) 振る舞いを直接教える | **採用**。5 分の学習で「宇宙について教えて」に文脈の文を組み合わせた応答が出るようになった |
| 次数の選択 | 実験 [1]: 数千文では 3 次と 4 次の ppl が同じ (28.2)。4 次はエントリ 1.8 倍 | **既定を 3 次に変更**。`TINYAI_MAX_ORDER=4` で戻せる |
| 小型ニューラル LM (純 Python) | 埋め込み + 1 層 RNN 程度でも学習が数十倍遅く、オンライン学習と両立しない | 不採用 |

## 2. 検索・知識

| 技術 | 要点 | 判断 |
|---|---|---|
| BM25 + 語の情報量重み + カバー率 | かな bigram を弱く、漢字/カタカナ語・英単語を強く | **採用** |
| 動的ストップ語 | 文書の 20% 以上に出る語は他に語があれば無視 | **採用** (大規模化に伴う検索コストの抑制) |
| 転置索引の投稿の整数パック | 1 件だけの語は辞書を作らない | **採用** |
| 近似重複の排除 (content key) | 句と数値トークンの集合のハッシュ。MinHash/SimHash の最軽量版 | **採用**。ほぼ同じ文の再学習を取り込み時点で防ぐ |
| 分布的な関連語 (PMI) | 学習時は何も計算せず、必要時に転置索引から共起を数える | **採用** (クエリ拡張)。学習コストゼロ |
| 学習型スパース検索 (SPLADE 等) / 密ベクトル (HNSW) | 学習済みモデルが必要、または numpy なしでは遅い | 不採用 |
| Random Indexing (Kanerva 1988, Sahlgren 2005) | 語ごとの疎な乱択ベクトルを文脈に足し込むだけの分散表現。word2vec のオンライン・超軽量版 | **採用** (`semantic.py`)。1 文 60µs、128 次元 int16 (語あたり 256 bytes)。近傍探索は 64 bit SimHash (疎な超平面) で候補を絞ってからコサイン。質問と文の意味類似をリランクに混ぜる |
| 学習型リランカー (learning to rank の最小形) | 👍/👎 と教えた答えを正例/負例にロジスティック回帰をオンライン学習 | **採用** (`reranker.py`)。12 特徴量、1 サンプル数 µs。確信度への混ぜ方は進化パラメータ |
| 知識グラフ (GraphRAG の考え方) | 文から主語-関係-目的語を抽出して事実ストアに保持し、質問を (主語, 関係) に分解して引く | **採用** (`facts.py`)。多段の質問 (「AのBのCは？」) も連鎖検索で答える |
| Wikidata の構造化データ | 検索 API の説明文を定義事実として取り込める | **採用** (収集ソース `wikidata`) |

## 5. 実験結果 (日本語 Wikipedia 3 記事、約 940 文)

```

order disc   ppl  entries  sec            tokens=51712 build=0.04s 45 bytes/token
  2  0.75  38.51   16679  0.027           count-queries=162641/s
  3  0.75  28.21   45594  0.055
  4  0.75  28.24   82887  0.090
  5  0.90  28.35  124725  0.127
```

学習速度の推移 (tools/bench.py、同一コーパス):

| 版 | 学習速度 | 実メモリ増分 | 自問自答の的中 |
|---|---|---|---|
| 初版 | 5,243 文/秒 | 26.4MB | 0.878 |
| 整数パック | 5,053 文/秒 | 13.1MB | 0.845 |
| 事実抽出・品質採点 | 4,668 文/秒 | 13.1MB | 0.845 |
| 3 次既定・正規表現化・近似重複排除 | 5,594 文/秒 | 7.9MB | 0.834 |

的中率の低下分は、定義質問のリランクと近似重複排除 (自問自答の元の文が「重複」として落ちる) によるもので、
実際の会話の質は `tools/eval.py` の評価セットで測る。

### 実験 [4] 純 Python 小型ニューラル LM

```
vocab=1834 pairs=40000 epochs=2 学習 15.0s (5335 token/s) 評価 4.2s (完全 softmax)
ppl: neural=121.3  KN-bigram=37.2  KN-trigram=28.2
```

結論: 数万トークン・純 Python では、ニューラル LM は速度でも精度でも n-gram に勝てない。
「LLM らしい」振る舞いは分散表現 + 長文脈 (接尾辞配列) + 会話キャッシュ + フィードバック学習の組み合わせで得る方が、
この制約では費用対効果が高い。numpy が使える環境なら再検討の価値がある (行列積が 100 倍速くなる)。

## 5b. 評価システム

評価は `tools/eval.py` に集約した。会話評価 (カテゴリ別: 事実・多段・文脈・訂正・言い換え・雑談・未知への正直さ) は
期待語だけでなく **禁止語・応答モード・確信度の条件** を書けるようにし、言い換えは自動生成する。
コーパス指標は検索 (MRR / Recall@3)、LM (取り置き文の ppl)、生成 (distinct-2、4-gram 接地率、繰り返し率)、
学習速度、メモリ。結果は `eval/results.jsonl` に追記して前回と比較できる。

評価の刷新が直接見つけた不具合: (1) 英語の文が「文字種が少ない」ためジャンク扱いで落ちていた
(英語 Wikipedia の文が学習されていなかった)、(2) 句が 3 つ以下の短文が近似重複で落ちていた、
(3) 「富士山の面積は？」に標高で答えていた、(4) 👍👎 が数件の段階で学習型リランカーが順位を乱していた。
評価の網羅性が品質を直接押し上げるという教訓。

## 5c. 多出典投票と矛盾の可視化

事実 (主語, 関係, 目的語) を目的語の正規化形でまとめ、支持する出典の数で順位付けする。
近似重複で取り込みを見送った文も、出典が違えば元の文の裏付けとして数える (取り込みコストゼロで信頼度が上がる)。
最有力を答え、食い違う説があれば「別の出典では…」と添える。真偽の判定はしない (できない) が、
利用者が判断できる材料を出す。

## 5f. リアルタイム学習と進化 (ニューラル LM)

* **オンライン学習**: 各ターン直後に (発話, 応答, 文脈) を 1 系列 + 再生バッファ 3 系列のバッチで 1 ステップ更新 (学習率は通常の半分)。
  再生を混ぜるのは破滅的忘却を避けるため (経験再生)。
* **unlikelihood 学習** (Welleck et al. 2019): 👎 の応答は L = −log(1 − p) で確率を下げる。勾配は交差エントロピーの
  −p_t/(1−p_t) 倍で、係数は 5 で頭打ち。テスト: 負例の対数尤度 −0.10 → −7.4、正例は −0.13 → −0.02 のまま。
* **関数保存の成長** (Net2Net / 段階的成長): 新しい層の出力射影をゼロで初期化して追加すると、追加直後は恒等写像で
  既存の振る舞いを壊さない。損失が 10 ステップ平均で 0.02 未満しか改善せず、かつ 1.5 以上の時に発動。上限はプリセットごと。
* **語彙の進化**: 新しいテキストに頻出する未知の 2〜4 文字単位を語彙に追加し、埋め込み行を既存の平均 + 微小乱数で初期化。
* **復号パラメータの進化**: 温度・top-p・繰り返しペナルティを 👍 率で山登り (6 件ごとに 1 パラメータを試行、悪化なら戻す)。

## 5e. エージェント層 (道具の使用)

ChatGPT や Gemini の「賢さ」のうち、この規模で再現できるのは主に周辺の知能である:
計算・日付・単位は言語モデルに推測させず道具で正確に解く (LLM でも tool use として標準化された考え方)、
比較は事実の数値を取り出して判定する、列挙は知識文の並列表現から抽出する、要約は抽出型、
未知の話題はその場で収集して学んでから答える (検索拡張の同期版)、利用者の情報は明示的なプロファイルとして持つ。
道具の出力は確信度 1.0 で返し、書式指示は答えの後処理として適用する。
評価 (tools / profile / format カテゴリ 18 問) は全問正解。

## 5d. 会話データ

Wikipedia のような説明文だけでは「会話」の分布を学べない。自分の会話 (👍 付きは重み 3 倍) に加え、
Hugging Face datasets-server (公開データセットの行を JSON で返す) から対話/指示データ、Stack Exchange API から
質問と採用回答、青空文庫からは「」の応酬を抽出して、`<usr>` 発話 `<bot>` 応答 `<eos>` の形式でニューラル LM に流す。
個人情報らしい文字列 (メールアドレス・電話番号) は保存前に落とす。

## 5g. 学習効率と知能の強化 (第 3 期)

評価システムで測って初めて分かった弱点と、その対策:

| 発見 | 対策 | 効果 |
|---|---|---|
| 1.1 万系列 (55 万トークン) を 5,000 ステップ回すと学習損失 0.45 なのに取り置き ppl 19 (過学習) | pending 上限を迂回して全知識文 (3 万系列 / 124 万トークン) をプールへ、ドロップアウト 0.1、優先再生 (損失^0.6、半分は一様) | 同じモデルで ppl 19.4 → 12.2 (10 分) |
| 生成が検索文脈をほとんど使わない (RAG 忠実性 0.015、キーワード再現 0) | 写し取り練習を 20 例/回 → 1.2 万例 (文脈の中の正しい文を選ぶ。無関係な文を 3 割混ぜ、位置も散らす) | 本文の実測値を参照 |
| 読込直後 (再生バッファが空) は learn_turn が何もしない (online_gain 0) | バッファが空ならそのターンだけで学ぶ | 即時学習が常に働く |
| データ並列のワーカーは fork 時点のバッファしか見ない (収集したデータが学習に入らない) | 親の追記記録をパイプでワーカーへ同期 | 収集 → 1 分以内に学習 |
| ストリーム源の選択が既に成功した源に偏る (青空文庫ばかり、HF 対話データ 0) | 未試行の源は点数 1.0 (楽観的探索)、HF は 100 行/回・重み 1.5 | 1 分に 100 会話 |
| 語彙進化の直後に並列学習が落ちる (埋め込みの形の不一致) | 形を変える前にワーカーを止めて作り直す | 修正 |

第 4 期 (継続学習の実運用で分かったこと):

| 改良 | 理由 | 実測 |
|---|---|---|
| 文脈長 128 → 256 (`extend_context`) | RAG の文脈が T/2 = 64 トークンしか入らず、検索した文が途中で切れていた | 1 ステップの時間はほぼ同じで処理トークン 1.4 倍。重みの形は不変なので学習済みモデルをそのまま伸ばせる |
| 学習率を WSD (ウォームアップ後は一定) | 終わりの無い継続学習でコサイン減衰は「総ステップ数」を決め打ちする必要があり、途中で学習率が枯れる。減衰の役割は EMA が担う | 学習を止めずに学習率を保てる |
| 出力層を「損失に効く位置」だけで計算 | 負例や短い系列はパディングが多く、語彙全体への射影 (1 ステップの計算の約半分) が無駄になる | 無効位置 32% の時、出力層の順伝播 + 逆伝播が 182 ms → 104 ms (43% 削減) |
| 選好データ (chosen / rejected) を正例 + 負例に | 良い答えを覚えるだけでなく、悪い答えを避ける方向にも勾配をかける (DPO の簡易版を unlikelihood で) | hh-rlhf 日本語版 12k を投入 |

**文脈語への復号バイアス (写し取りの手掛かり)**: 小さなモデルは文脈を無視して「それらしい文」を作りがちで、
RAG 忠実性が 0.05 程度しか出なかった。生成の各ステップで、文脈 (検索した文) に現れるトークンの対数確率に
定数 b を足すだけで、追加の順伝播なしに接地率が上がる (Context-aware decoding の簡易版)。
同じチェックポイント (11,235 step) での実測、取り置き 49 文・各 2 回平均:

| b | 接地率 | キーワード再現 | 自然さ (平均対数確率) |
|---|---|---|---|
| 0.0 | 0.120 | 0.173 | −2.05 |
| 1.5 | 0.232 | 0.306 | −2.05 |
| 2.0 | 0.310 | 0.337 | −2.05 |
| 3.0 | 0.421 | 0.429 | −2.22 |
| 4.0 | 0.512 | 0.459 | −2.37 |
| 5.0 | 0.544 | 0.541 | −2.46 |

既定は 3.0 (接地率が 3.5 倍になり、自然さの低下は 0.17 nat)。👍/👎 の山登りで 0〜5 を探索する。
ブラウザ版にも同じ仕組みを実装した。

**学習時の文脈を本番に合わせる**: 写し取り練習の文脈を「その文 + 隣の文」だけで作ると、
「文脈の先頭を写す」癖がつき、本番の検索結果 (順番も内容も違い、答えの文が入っていないこともある) で効かない。
半分の例は**実際にその質問で検索した結果**を文脈にする (答えの文は検索結果に混ぜ込む)。
1.2 万例を作るのに 11 秒。

**再生バッファのメモリ**: 学習系列を Python のリストで持つと 1 トークンあたり約 36 バイト
(int オブジェクト 28 + ポインタ 8)。int32 配列にすると 4 バイトで、280 万トークンなら 101MB → 11MB。
メモリ上限に当たって知識文が削られていた原因の一つで、同じ上限でより多くの記憶を保てるようになる。

**混ぜ方の偏り**: 自動評価で RAG 忠実性が 0.31 → 0.82 と伸びる一方、取り置き文の ppl が 17 → 21 に悪化した。
写し取り練習 (文脈から答える会話形式) が再生バッファを占め、自由な文生成の力が落ちていた。
系列に種類 (text / dialog / copy / qa) を持たせ、写し取りは 30%、合成 QA は 15% を上限にした。

**評価の固定**: 会話 ppl を「直近の会話」で測っていたため、その時に集めたデータセット次第で 24 〜 945 と
揺れて比較にならなかった。一度選んだ取り置き会話 (乱数種固定、保存・復元される) で測るようにした。

**会話のキャッチボール**: 1 往復だけを学習・生成していたため「それはどういう意味？」のような指示語が効かなかった。
学習系列と生成プロンプトの両方に直前のやり取りを入れ (予算は文脈長の 1/3)、損失は最後の応答だけに掛ける。
公開データセットの多ターン会話も流れごと取り込む。ブラウザ版でも同じ形式にし、2 ターン目で
「それはどういう意味？」に文脈を踏まえた応答が返ることを確認した。

**幅の成長 (Net2WiderNet)**: 層が上限に達した後の容量の増やし方。MLP の中間単位を複製し、出て行く重みを
半分ずつに分けると出力が変わらない (実測の出力差 0.003、雑音による対称性の破れ分)。深さと幅を順に伸ばせる。

**EMA の落とし穴**: 平均重み (EMA) を評価・生成・書き出しに使っていたが、学習率を一定 (WSD) にして
速く動かすと EMA が追いつかず、実測で生の重み ppl 24 に対し EMA は 253、生成も崩れていた
(「、わた・)(()は))の実現オオ・・・」)。評価のたびに EMA と生の重みの ppl を比べ、EMA が 5% 以上悪ければ
生の重みに切り替えて EMA を作り直すようにした。書き出しも同じ判断に従う。
平均重みは「学習率を下げる代わり」に使えるが、**効いているかを測らずに使ってはいけない**。

**復号の松葉杖は外せる**: 導入時 (step 1.3 万) は文脈語への復号バイアスが接地率を 0.12 → 0.42 に上げたが、
写し取り練習で学習が追いついた後 (step 1.5 万) に測り直すと、**バイアス 0 でも接地率 0.889**、
3.0 でも 0.928 で、差は 0.04 しかない。一方で自然さ (平均対数確率) は −2.996 → −3.076 と落ちる。
既定を 3.0 → 1.0 に下げ、指示語で始まる発話や検索が弱い時はさらに 0.3 倍にする。
**学習で身に付いた能力は、復号時の細工を外して確かめる**。外せるなら外した方が自由な生成が良くなる。

その他の追加:

* **損失マスク**: 会話系列のプロンプト部 (文脈・発話) は重み 0.2、応答部 1.0。同じ計算量で応答の質に勾配を集中させつつ、
  文脈の言語モデル信号も少し残す (完全にマスクすると文脈を読む力が育たない)。
* **EMA 重み** (Polyak 平均、減衰 0.998): 評価・生成・書き出しは EMA 重みで行う。小型モデルを大きな学習率で回す時の
  揺れを平均し、取り置き ppl が安定する。
* **埋め込みの勾配**: one-hot 行列積 (V × BT × d = 1.7 GFLOP/ステップ) を並べ替え + 区間和にして 5 倍速。
* **2 段階の思考**: 下書き → 下書きの句で再検索 → 文脈を広げて再生成 → 接地率 + 自己対数確率で検証。
  再検索で文脈が増える割合は 0.7〜0.9 (評価 think_rethink_rate)。
* **データの価値評価**: 収集ページの「驚き」(ニューラル LM の平均トークン損失 nat) を学習前に測り、2〜5 nat を最良とする
  価値をソースの点数に掛ける。既知 (1 nat 未満) と ジャンク・別言語 (6 nat 超) を自動的に避ける。
* **ブラウザ版**: int8 書き出し (3 MB) + JS で順伝播・逆伝播・AdamW を移植 (numpy と logits・損失・勾配が一致)。
  会話ごとの更新に加えて常時学習 (3 秒ごとに 1 系列)。学習ステップ ≈ 0.5〜1 秒 (T=50、3M パラメータ)。

**ループを止めるのは繰り返しペナルティではなく n-gram 禁止**: 既存の繰り返しペナルティ (直近 20 トークンの
再出現を 1.3 で割る) は「同じ単語を二度使うこと」を一律に罰するので、助詞や「です」が犠牲になり文が不自然になる。
代わりに **no-repeat-ngram (3)** を入れ、「直前の 2 トークンと同じ並びの後に一度出たトークン」だけを禁止した。
step 15,906 の重みで 8 種類の質問 × 2 候補を測ると、3-gram の重複率 **0.027 → 0.013**、平均長 37.1 → 41.0 文字。
言い回しのループだけが消え、語の再利用は残るので文が短く切れない。合わせて **min_new = 6** で終端トークンを
最初の数トークンだけ抑制し、「はい。」だけの返事を防ぐ。

**既定値の世代管理**: 復号設定はチェックポイントの meta に保存され、起動時に復元される。そのため研究で既定値を
下げても (copy_bonus 3.0 → 1.0)、古いチェックポイントが 3.0 を書き戻して**改善が無かったことになっていた**。
meta に `decode_version` を持たせ、世代が古ければ見直した項目だけ既定値から再開する。
**保存された設定は、研究の結論を静かに上書きする**。

**多ターンの履歴は保存しなければ学習されない**: 収集器は会話データセットから直前のやり取りを取り出して
`(発話, 応答, 文脈, 重み, 履歴)` として渡していたが、保存側 (DialogStore) は `(発話, 応答, 出典, 重み)` の
4 つ組しか持っておらず、**履歴はその場で 1 回学ばれて捨てられていた**。再生バッファは再起動のたびに
保存済みの会話から積み直されるので、10 分ごとに学習を再開する運用では実質すべての会話が単ターンだった
(= 過去の発話を踏まえて答える練習が一度もできていない)。履歴を 2 組・各 120 文字まで保存するようにし、
積み直しでも `seq_dialog(..., history=...)` に渡す。記憶量の増加は 2 万組で約 4 MB。
**「学習データに入っているつもり」は測って確かめる** (`dialogs.with_history` を統計に追加した)。

**取り置き ppl の悪化は「忘却」だった**: step 1.3 万から 1.66 万にかけて取り置き ppl が 17 → 27.6 に悪化する一方、
学習損失は 2.05 前後で平ら。step 16,618 の重みで内訳を測ると、**固定の取り置き 33.7 (日本語 36.8 / 非日本語 22.6)**
に対し、**現在の知識ベースから引いた文は 24.8 (日本語 26.0 / 非日本語 14.2)**。つまり「今のデータには合っているが、
最初の頃の文を忘れている」。原因は再生バッファの入れ替えが純粋な先入れ先出しだったこと: 収集が進むほど
古い系列が押し出され、10 分ごとに再起動する運用ではさらに偏る (2 万件をこれまでに 148 万件で置き換えていた)。

対策として**二段階の再生バッファ**にした。容量の 25% は貯水池抽出 (確率 R/seen で無作為の枠を置き換える)
で「これまでに見た全系列の一様標本」を保ち、残り 75% は先入れ先出しで新しいデータに追従する。
容量 2,000 に 20,000 件を流す模擬実験で、古い 25% の時期の系列の残存率は **0.000 → 0.066**、最古の系列も残る。

**評価の分離**: 固定の取り置き 300 本 (忘却の検出) に加えて、**入れ替わる取り置き 150 本** (今の分布での汎化) を
持つようにした。この 2 つの差が忘却の量そのもので、片方だけを見ていると「悪化」と「分布の移動」を取り違える。

**多ターン会話はどこにあるか**: 公開データセットを実測すると、同じ「会話形式」でも多ターンの割合は大きく違う。
Hugging Face の 40 行ずつで測った履歴つきペアの割合は **shi3z/ja_conv_wikipedia 78%、llm-jp/oasst2-33k-ja 40%、
llm-jp/magpie-sft-v1.0 0%** (magpie は会話形式だが実質 1 往復の指示データ)。
さらに、選好データ (hh-rlhf 系) は最後の発話しか使っておらず手前のやり取りを捨てていたので、履歴として付けるようにした。
青空文庫の「」の応酬も、地の文で途切れない限り同じ会話として履歴をつなぐ (人間どうしの自然な多ターン会話の数少ない供給源)。

**再生バッファを持ち越さないと、バッファの工夫は全部無駄になる**: 再生バッファは再起動のたびに
「知識文 3,000 + 直近の会話 3,000」から作り直していた。10 分ごとに学習を再開する運用では、貯水池抽出で
残した古い系列も、優先再生の優先度も、種類ごとの混ざり具合も毎回失われ、ウォームアップの時間も毎回かかる。
系列を連結した int32 配列 + 区切り位置 + 重み + 優先度 + (capacity, pos, seen, reservoir) として
1 つの npz に保存し、起動時に読み戻すようにした (2 万系列・280 万トークンで約 11 MB)。
**続きから学習する仕組みは、重みだけでなくデータの側にも要る**。

**成長が止まっていたのは条件ではなくバグだった**: 層は上限 9 に対して 6 のまま止まっていた。原因は
「過学習中は成長させない」を入れた改修で損失の停滞判定に使う変数の代入行を消してしまい、
そこに到達すると NameError で落ちていたこと (直前の悪化ガードが先に働くため、ほとんどの回で
その行まで届かず、エラーが表に出るのが遅れた)。テストは成長の呼び出し自体を通していなかった。
**「守り」の条件を足す改修は、守りが働かない経路のテストも要る**。

あわせて、悪化ガードの判定を固定の取り置きから**入れ替わる取り置き**に変えた。固定の取り置きには
学習データから外れた古い文が含まれるので、忘却による悪化と過学習による悪化を区別できない。
忘却が理由なら、容量を増やすのはむしろ正しい対処になる。

**取り置き ppl が上がり続ける本当の理由: 再生バッファが会話で埋まっていた**: 保存したバッファ 3 万系列の
内訳を数えると **会話 23,986 (80%) / 平文 3,673 (12%) / 写し取り 1,021 / 合成 QA 1,320**、日本語 88%・英語 12%。
取り置きは平文なので、平文が痩せれば取り置き ppl は上がる。収集は 1 回の巡回で会話を 100〜400 組も持ち帰る一方、
平文は知識文として貯まるだけなので、放っておくとバッファは会話一色になる。会話にも上限 (0.55) を置いた。
流入比を会話 70% で模擬すると平文は **12% → 30%** に戻る。

**比率の上限は容量に対して見る**: 上限の判定を「現在の件数」に対して行っていたため、詰め始めの数件で比率が
跳ね上がり、その種類がほとんど入らなくなっていた (空のバッファに会話 500 件を入れると 1 件しか残らない)。
分母を容量に変えた。**比率の分母を間違えると、上限は「上限」ではなく「ほぼ禁止」になる**。

**同じ系列を 41 周していた**: 学習損失は下がるのに取り置き ppl が上がり続ける (1.94 / 30.8) 状態を数字で追うと、
再生バッファは 3 万系列 = **276 万トークン**なのに学習済みトークンは **1.13 億** — つまり手持ちのデータを
約 41 周している。3.8M パラメータに対しトークンは 276 万 (1 パラメータあたり 0.7 トークン) しかなく、
過学習して当然だった。容量が既定の 3 万で固定だったのが原因で、メモリ 1 GB を与えても増えない。

容量を **メモリ 1 MB あたり 100 系列** (1 GB で約 10 万系列 ≒ 37 MB) に比例させ、起動時にバッファが容量の
半分に満たなければ手持ちの知識文 (4.9 万件) と会話 (2.8 万組) で埋めるようにした。
**周回数を減らす一番安い方法は、バッファを大きくして手持ちの文を一度ずつ通すこと**。

**自由生成が弱いのは学習量の不足**: 生成させると文としては流暢だが意味が通らない
(「好きな本は『良い』という言葉の正しい表現です」)。数字で見ると、再生バッファ 10 万系列 = **717 万トークン**に対し
パラメータは 386 万、つまり **1.86 トークン/パラメータ**。Chinchilla 則の目安 20 トークン/パラメータ なら
7,700 万トークン必要で、**桁が 1 つ足りない**。しかも読んだ文の大半は知識ベースのメモリ上限で捨てられ、
二度と学習に使われていなかった。

対策として**ディスクの追記型トークンコーパス** (環状バッファ) を入れた。トークン列は int32 で 1 トークン 4 バイト
なので、1 GB のメモリ設定でも 8,200 万トークン (328 MB) をディスクに置ける。読んだ文と会話はすべてここに書き足し、
学習のたびに一部を再生バッファへ戻して循環させる。RAM を増やさずに「一度読んだ文をもう一度学ぶ」経路を作るのが狙い。

**1 文ずつ学ばせていたら、1 文ずつしか書けない**: ニューラル LM に渡す平文は「取り込んだ文を 1 つずつ」
だった (平均 92 トークン)。文脈長は 256 あるのに、系列の実体は短い断片ばかりで、しかもバッチは無関係な断片を
<eos> で継ぎ足して埋める。つまり**段落の流れを一度も学んでいない**。生成が 1 文ごとに話題を変えるのはこれが直接の原因。
同じ出典の連続した文を 350 文字 (≒ 文脈長) までまとめてから渡すようにした。実測で 1 系列あたり平均 323 文字、
最大 411 文字。

**知識ベースと学習コーパスは別物として扱う**: 読んだページは知識ベースを通していた。知識ベースは重複判定・
品質判定・事実抽出・意味ベクトルまで行うので重く、メモリ上限で古い文書から捨てられる。一方、言語モデルの学習に
必要なのはトークン列だけで 1 トークン 4 バイトしかない。そこでページ本文は**丸ごとディスクのコーパスにも流し込む**
ようにした (段落ごとに文脈長で切って詰める)。10 KB のページ 1 枚で約 9,000 トークン入る。
知識ベースの大きさ (検索の質) と学習トークン量 (生成の質) を別々に増やせるようになった。

**成長の引き金にデータ量を加える**: これまで容量を増やす条件は「損失が停滞したら」だけだった。しかし
学習量が増えている局面では損失はまだ下がり続けるので、いつまでも成長しない。Chinchilla 則の考え方で
**「手持ちのトークンがパラメータ数の 20 倍を超えたら先回りして大きくする」**という条件を足した
(どちらの場合も「今の分布での取り置き ppl が悪化していない」ことが前提)。
本文の一括取り込みを入れた直後の 5 分でコーパスは **684 万 → 1,394 万トークン**に倍増しており、
この調子なら 386 万パラメータの容量 (7,700 万トークン) を数十分で超える。

**容量設定を変えたら貯めたデータが消えた**: コーパスの上限を 4,100 万 → 8,200 万トークンに上げた途端、
蓄積が 1,394 万 → 371 万トークンに戻った。読込時に「容量が変わったら索引を捨てる」と書いていたためで、
**上限を上げる = 貯める気の変更なのに、貯めたものを捨てる**という最悪の挙動だった。
増やす時は既存の位置がそのまま有効なので索引を保ち、減らす時は収まる系列だけ残すようにした
(ファイルの大きさも開くときに合わせる)。**設定の変更でデータが消える経路は、変更した瞬間に気づけない**。

**壊れた書式を学ばせていた**: 生成に「1.**生inger**:」のような壊れた箇条書きが現れるのは、学習データが
そうなっているから。保存済みの会話 3.1 万組を数えると **8% にマークダウンの書式が混入し、6% は途中で終わっている**
(指示データの応答は「説明文 + 番号つきの箇条書き」が多く、220 字で切り詰めると箇条書きの途中で切れる)。
応答を保存する時に書式記号 (**, ##, `) を落とし、箇条書きが始まる手前の地の文までを学習対象にした。
**小さなモデルには書式より地の文を学ばせる**。

**貯めたトークンの 3 割はゴミだった**: コーパスから 200 件を抜き出して調べると、**64 件 (32%)** が
「文末記号がほとんど無い」「数字だらけ」「どの言語の地の文とも言えない」のいずれかだった (目次・ナビゲーション・
表・統計の羅列)。さらに Hugging Face の欠損値が文字列 "nan" のまま本文に混ざっていた
(「…曲を見つけてください。 nan切なくて穏やかな…」)。量を増やす改修の直後に質の検査を挟むのは必須で、
**量だけ増やすとゴミも比例して増える**。句読点・数字・文字種の割合という安い規則で落とすようにし、
データセットの欠損値も除くようにした。

**候補を n 本出しても同じ文なら意味が無い**: 学習ログの生成例で 2 本の候補がまったく同一だった。
検索文脈が強い時は分布が尖り、同じ温度で引けば同じ文が出る。候補ごとに温度を変える (中心の 0.7 に対し ±25%) と、
検索文脈つきの 4 本の異なり数は **3.00 → 3.33**。文脈なしの雑談では元から 4.00 で差は出ない
(尖っていないので当然)。**多様性の対策は、尖っている時にだけ効く**。重複した候補は 1 本にまとめるようにもした。

なお同じ時点の生成例は 1 時間前より明らかに良くなっている:
「機械学習とは、データから学習し、その結果を得た一連のタスクに分割する手法です」(14:09 は
「好きな本は『良い』という言葉の正しい表現です」)。段落単位の学習とコーパスの効果が出始めている。

**「長い系列で学ぶ」は入口を全部直さないと効かない**: 段落単位で渡すようにした後もバッファの平文は
平均 63 トークン (中央値 39) のままだった。内訳を見ると 2.8 万本のうち **9,348 本が 32 トークン未満、
13,271 本が 32〜64**。原因は起動時の補充で、知識ベースの文書を 1 件ずつ `add_text` に渡していたこと
(知識ベースは 1 文 = 1 文書なので、必ず短い系列になる)。補充もコーパス優先 (段落単位の長い系列) に変え、
知識ベースから採る時は文をつないでから渡すようにした。
種類別のトークン比は 会話 59% / 平文 21% / 写し取り 16% / 合成 QA 4% (系列数では 55/28/11/6)。
**比率は系列数ではなくトークン数で見ないと、実際の学習量を見誤る**。

**長い系列を優先して引き戻す**: コーパスには 1 文だけの短い系列も残っているので、無作為に引くと
再生バッファの平均長は上がらない。候補を 2 倍引いて長い方の半分を返す仕組みを入れた
(短い系列と長い系列が半々の模擬データで、平均長 119 → 200)。再起動を待たずに、学習中の入れ替えだけで
バッファの平文を段落単位に置き換えていける。

**「20 トークン/パラメータ」は飽和の判定基準ではない**: 1 時間でコーパスを 684 万 → 2,495 万トークンに
増やす間、学習損失は 1.79 → 2.00、固定取り置き ppl は 31 → 32.8、入れ替わる取り置きは 19.5 → 25.2 と、
そろって悪化した。データの多様性が急に増えたのに 386 万パラメータでは吸収しきれない = 容量不足の症状。
Chinchilla の 20 トークン/パラメータは「一から学習する時の計算最適」であって、飽和の判定基準ではない。
そこで成長の条件を 2 段にした:

* 強い条件: トークン数 > 20 × パラメータ数 (計算最適の目安を超えた)
* 弱い条件: トークン数 > 5 × パラメータ数 **かつ** 入れ替わる取り置き ppl が良くなっていない
  (データが増えても良くならない = 容量が足りない、という直接の証拠)

急激な悪化 (25% 超) は学習の不安定なので、その時は成長させない (従来は 15% で止めていたが、
データが広がった時の緩やかな悪化まで止めてしまい、いちばん成長すべき局面で成長しなかった)。

**成長を止めていたのは条件ではなくメモリガードだった**: 成長の条件を整えても層は 6 のまま。調べると
`guard.pressure() < 0.7` で弾かれていた (実測の圧力 0.77)。圧力の中身は知識ベース・再生バッファ・コーパスの索引で、
**モデル自身の成長コストは 1 層あたり 6.8 MB** (重み + Adam の 1 次/2 次 + EMA) しかない。
データ側が上限に近いことを理由にモデルの成長を止めるのは、いちばん容量が要る局面で成長を諦めるのと同じ。
判定を「今の圧力 + 成長で増える分 < 0.95」に変えた。データ側は自前の刈り込みで縮む。
**ガードは「何を守るためのものか」を見て、対象ごとに分ける**。

**層 7 へ成長 (16:38, 431 万パラメータ)**。新しい条件のうち「弱い条件」(トークン数 > 5 × パラメータ数 かつ
今の分布での ppl が良くなっていない) が発火した。成長直後の生成:
「人工知能とは、人間の知的行動をコンピュータで構成する能力のことです」。

**語彙の候補は「実際に減るトークン数」で選ぶ**: 1 トークンあたり **1.45 文字**しかなく (日本語なら 2 前後が目安)、
語彙の追加候補の上位は velo / elop / deve のような英単語の断片だった。順位付けが「(文字数 - 1) × 頻度」で、
**既にうまく分割できている英語の断片が上位に来てしまう**のが原因。今の語彙で符号化した時の実測の削減量
((現在のトークン数 - 1) × 頻度) に変えると、上位は 設立・言葉・幽霊・化学・ドイツ・マグマ のような日本語の語になった。
200 語の追加で 1.54 → 1.59 文字/トークン。候補は知識ベースではなく学習コーパスから採り、1 回の追加を 50 → 150 語にした
(1 語の追加コストは埋め込み 192 次元 × 4 系列 = 約 3 KB と安い)。

**成長は速すぎても悪い**: 条件を緩めた途端、層は 12 分で **7 → 8 → 9** と 3 段増えた (386 万 → 520 万パラメータ)。
その間に入れ替わる取り置き ppl は 24.7 → 27.5 → 30.1、対話 ppl は 75 → 89 と悪化している。
Net2Net で関数は保たれるが、**増えた容量が使えるようになるには学習の時間が要る**。間を置かずに増やすと
「増やす → 一時的に悪化 → 悪化を見てまた増やす」の悪循環になる。成長後 800 ステップは次の成長を待つようにした
(この間隔はチェックポイントに保存し、再起動をまたいでも守る)。

**成長の後は学習率を下げてから戻す**: 3 層追加の後、間隔を空けても回復しなかった
(対話 ppl 75 → 89 → 98、損失 1.93 → 2.04、速度も 7,400 → 5,000 tok/s)。
追加した層は恒等写像から学び始めるので、そこへ通常の学習率をかけると、**既に学んだ重みの方が崩れる**。
成長直後は 0.3 倍から始めて 400 ステップかけて戻すようにした (Net2Net 系の改造では標準的な扱い)。
関数を保つ成長でも、**学習率まで含めて「保つ」設計にしないと意味がない**。

**深くしたら学習率を下げる**: 成長直後のウォームアップを入れても悪化は止まらなかった
(対話 ppl 98 → **118**、接地率 0.95 → **0.83**、固定取り置き 32.5 → 33.5)。原因は、プリセットの学習率
6e-4 が **4 層のときに合わせた値**だったのに、9 層まで増やしてもそのまま使っていたこと。
残差の重なりが深くなるほど、同じ更新幅でも出力の変化は大きくなる。深さの平方根に反比例させる
補正を入れた (9 層で 6e-4 → 4e-4、成長直後のウォームアップと合わせて一時的に 1.2e-4)。
**成長させる仕組みを作るなら、成長に合わせて変える必要がある量を全部洗い出す**。

**深さ補正の効果**: 学習率を 6e-4 → 4e-4 (深さの平方根に反比例) に下げた 10 分後、
入れ替わる取り置き ppl は **35.8 → 25.3**、接地率は **0.83 → 0.92**、対話 ppl は 117.6 → 107.1 と回復に向かった。
悪化の原因は容量ではなく学習率だったと確認できた。

**成長は取り消せるようにする**: 成長は元に戻せない操作で、裏目に出ると 1 時間分の学習が傷つく
(今回は対話 ppl 75 → 118 まで悪化した)。成長の直前に重みを別ファイルへ保存し、
間隔 (800 ステップ) を置いた後に成長前の ppl と比べて 1.4 倍以上悪ければ自動で戻すようにした。
**不可逆な自動変更には、必ず検証と巻き戻しを付ける**。

## 6. 次の実験候補

1. 因子分解した埋め込み (V×r → r×d) でパラメータの 4 割を占める埋め込みを縮め、その分を層に回す
2. RAG 忠実性の指標を目標に写し取り練習の割合を最適化 (多すぎると自由な会話が固くなる)
3. 自己対話 (自分の質問に自分で答え、検証で通ったものだけ学ぶ) による自己改善の実験
3. 要約回答の品質評価 (人手) と、文の順序付け (定義 → 属性 → 出来事) の学習
2. 事実の信頼度: 複数の出典で一致する事実を高く、矛盾する事実を低く (真偽の投票)
3. 関心プロファイルを検索のスコアに直接混ぜる (パーソナライズ)
4. 文の品質採点を 👍/👎 から学習する (ロジスティック回帰なら純 Python でも十分速い)
